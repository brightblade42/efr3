# `fr-api` Guide

`fr-api` is the HTTP interface for SAFR facial-recognition workflows.

This guide explains how to think about the API before you dive into the endpoint-by-endpoint
reference.

## Public Scope

The current public API is the `/fr/v2` route family.

The service also exposes:

- `/fr` - legacy compatibility routes for older clients
- `/tpass` - internal helper routes that are intentionally excluded from the public-facing docs

Use `/fr/v2` for new integrations.

## Request Styles

The API uses two main request styles.

### Multipart Endpoints

Multipart routes are used when an image upload is part of the request. Common fields include:

- `image` - required file upload or base64 image payload
- `opts` - optional JSON settings for recognition-style routes
- `details` - enrollment details for create-enrollment
- `profile` - TPass profile payload for create-profile

The server accepts either raw image bytes or base64-encoded image text and validates the result as a
recognized image format.

### JSON Endpoints

JSON routes are used when no image upload is needed, such as:

- enrollment deletion
- face deletion
- enrollment search
- profile edits
- alert requests

## Error Model

The most important thing to understand about `fr-api` is that it uses two categories of errors.

### Transport and Validation Errors

These are generated by Axum or request extraction and typically return HTTP `400` or `422`.

Examples:

- invalid multipart body
- missing required JSON fields
- wrong content type for strongly typed routes

### Application Errors

These are domain or business failures and are often returned as HTTP `200` with a standard JSON
error envelope:

```json
{
  "code": "DUPLICATE_ERR",
  "message": "an enrollment already exists that matches face",
  "details": {
    "ext_id": "1001",
    "fr_id": "i_12345",
    "score": 0.9912
  }
}
```

Common error codes include:

- `GENERIC_ERR`
- `INVALID_INPUT`
- `DUPLICATE_ERR`
- `QUALITY_LOW_ERR`
- `CREATE_ENROLLMENT_ERR`
- `DELETE_ENROLLMENT_ERR`
- `ADD_FACE_ERR`
- `MISSING_IMAGE_ERR`
- `REMOTE_ERR`

## Response Conventions

### Recognition Responses

Recognition returns an array of `FRIdentity` items. Each item contains:

- `face` - face-level data like bbox, quality, and optional liveness
- `possible_matches` - ranked match candidates

Each `possible_match` contains:

- `fr_id`
- `ext_id`
- `score` - raw numeric score used for matching logic
- `score_pct` - rounded percentage-style representation
- `details` - optional remote profile details

### Enrollment Responses

Create-enrollment returns an `IDPair`:

```json
{
  "fr_id": "i_12345",
  "ext_id": "1001"
}
```

### Face Management Responses

Face routes typically return either:

- an `EnrolledFaceInfo`
- a `DeleteFaceResult`
- a list of stored face records

## Legacy `/fr` Routes

The service still mounts several compatibility routes under `/fr`. They are useful for existing
clients but should be treated as transitional behavior rather than the main contract for new work.
